# Plan: Fix Dependency Vulnerabilities

## Context

`yarn npm audit --recursive` reports critical advisories in `tinypool` and `tar`, a high one in `ip`, a low one in `@tootallnate/once`, and moderate ones in `vitest`/`@vitest/mocker`. Currently `vitest` and `@vitest/coverage-v8` resolve to 3.2.7 (`tinypool@1.1.1`, `@vitest/mocker@3.2.7`), and `tar@6.2.1`, `ip@2.0.1` and `@tootallnate/once@2.0.0` enter only through the `node-gyp@9.3.1` / `make-fetch-happen` / `http-proxy-agent@5` / `socks@2.7.1` chain (dev tooling, not runtime). This plan upgrades `vitest` and its companion to 4.1.12 or later, then resolves the transitive packages by parent upgrade where possible and by `resolutions` otherwise. It follows `docs/features/004-fix-dependency-vulnerabilities/requirements.md` and is stage 1 of `docs/features/003-staged-dependency-updates`. Changes are limited to `package.json`, `yarn.lock` and vitest config files if a breaking change requires it.

---

## Options Considered

### Option A: Upgrade parents only
Find which direct dependency pulls in `node-gyp@9` and upgrade it.
**Pros**: No overrides to maintain.
**Cons**: The `node-gyp` chain probably comes from an optional native dependency of a tool with no newer release, so this may not clear `tar`, `ip` or `@tootallnate/once`.

### Option B: Upgrade parents, then `resolutions` for the remainder
Use `yarn why` to find the parent. Upgrade it if a release exists. Otherwise pin `tar`, `@tootallnate/once` (and `ip` if a fix exists) via `resolutions`.
**Pros**: Satisfies the requirements ordering (parent first, override as fallback); each override is documented and removable.
**Cons**: A major `tar` jump (6 to 7) under `node-gyp@9` is outside the declared range, so the dev-only install path must be verified.

**Chosen**: Option B. It is the only approach guaranteed to clear the critical `tar` advisory, and the requirements prescribe it.

---

## Files to Modify

| File | Change |
|---|---|
| `package.json` | Bump `vitest` and `@vitest/coverage-v8` to the same `^4.1.12` (or later); add `resolutions` for any transitive package that no parent upgrade fixes. |

| `vitest.config.ts`, `src/vitest.config.backend.ts`, `src/vitest.config.frontend.ts` | Only if the vitest 4 upgrade requires it (see step 2). |

## Implementation

### 1. Record the baseline
Run `yarn npm audit --recursive` and `yarn npm audit --recursive --json > $SCRATCH/audit-before.json`. Record package, severity, vulnerable range and chain for the PR description. Classify deprecation-only entries (`glob`, `rimraf`, `inflight`, `npmlog`, `gauge`, `are-we-there-yet`, `@npmcli/move-file`, `eslint`, `@mui/styles`) as non-exploitable and deferred. Also record baseline `yarn test` and `yarn build` timings for the 20% regression check, and run `yarn why tar`, `yarn why ip`, `yarn why @tootallnate/once` to identify the top-level parent.

### 2. Upgrade vitest and companions
```json
"@vitest/coverage-v8": "^4.1.12",
"vitest": "^4.1.12",
```
Run `yarn up vitest@^4.1.12 @vitest/coverage-v8@^4.1.12`. Confirm in `yarn.lock` that `tinypool` is `>=2.1.2` and `@vitest/mocker` is a fixed version. There is no `@vitest/ui` dependency. Check the vitest 4 migration notes against the configs: the root `vitest.config.ts` uses `test.projects` (supported) and `coverage.include`/`exclude` (vitest 4 requires `coverage.include` for uncovered files, which is already set). Fix `coverage.reportsDirectory` or reporters only if they error. Check vitest 4's Node engine floor (>=20) against `engines: >=18.12.0` and CI `vars.NODE_VERSION`. If it is higher, update `engines` deliberately and note it in the PR.

### 3. Resolve transitive packages
First run `yarn up -R` on the parent identified in step 1 and re-audit. For anything still vulnerable, add:
```json
"resolutions": {
  "tar": "^7.5.21",
  "@tootallnate/once": "^3.0.1"
}
```
Use the actual latest fixed versions shown by `yarn npm info`. Add `ip` only if a fixed release exists; otherwise document it as an accepted risk (reachable only via dev/build tooling `node-gyp` -> `make-fetch-happen` -> `socks`, never in the Express runtime or webpack bundle). Run `yarn install` and confirm `yarn why` shows the fixed versions.

### 4. Verify and revert on failure
Run the Verification commands. If an upgrade breaks something that cannot be fixed in scope, revert that package, record it as deferred, and continue. Commit as one `build(deps): ...` commit, separate from minor, patch and major update work (`commitlint.config.js` enforces conventional commits).

### 5. PR description
Include the baseline table, deferred list, the reason and removal condition for each `resolutions` entry (for example, "remove when `node-gyp` chain upgrades to `tar@>=7`"), accepted risks, and before/after audit output.

---

## Key Technical Decisions

- **Upgrade vitest directly rather than overriding `tinypool`**: Keeps the fix visible in `package.json`, and vitest 4 is the line containing the fixes.
- **`resolutions` for `tar` across a major**: `node-gyp@9` asks for `tar@^6`; this path is only used for optional native builds, so verify `yarn install` on a clean checkout rather than rely on semver.
- **No new dependencies**: Per the security non-functional requirement.

---

## Tests to Add

No new tests. Existing backend and frontend suites must pass unchanged without weakened assertions, and existing coverage settings must still work. The Playwright suite in `e2e/homepage.spec.ts` covers the production build.

## Verification

```bash
# 1. Lockfile reproducible
yarn install --immutable

# 2. Audit: no critical/high, except documented unfixable
yarn npm audit --recursive

# 3. Lint and build (build includes type-check via ts-loader)
yarn lint
yarn build

# 4. Unit tests with coverage (backend + frontend projects)
yarn test:coverage

# 5. E2E against production build
yarn test:e2e
```

Also compare `yarn test` and `yarn build` timings against the step 1 baseline (no more than 20% regression), and start the server in development (`yarn dev`) and production (`yarn start`) modes to confirm it serves the frontend and `/api/repo/:owner/:repo`.
