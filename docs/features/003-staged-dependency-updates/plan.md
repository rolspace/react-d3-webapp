# Plan: Staged Dependency Updates

## Context

The repo is a single Yarn 4.9.2 (Berry) project: `package.json` and `yarn.lock` at the root, `.yarnrc.yml` with `yarnPath` pinned to `.yarn/releases/yarn-4.9.2.cjs`, and Node 22 in the dev container. The `workspaces: ["src"]` entry is vestigial, because `src/` has no `package.json` and `yarn.lock` contains only the root workspace. Many dependencies have fallen behind and may carry advisories. This plan, derived from `docs/features/002-staged-dependency-updates/requirements.md`, upgrades them as three separately committed stages: (1) vulnerability fixes, (2) minor/patch updates, (3) major updates one package per commit. Every stage is gated by install, lint, test, build and a dev-server smoke test. The work is mostly manifest and lockfile changes, plus code or config changes only where a major bump forces them.

The requirements use Yarn 1 commands that do not exist in Yarn 4, so the plan maps them:

| Requirements says | Yarn 4 equivalent |
|---|---|
| `yarn audit` | `yarn npm audit --all --recursive` (add `--severity high` to gate) |
| `yarn outdated` | Not built in. Use `yarn upgrade-interactive` (built into Yarn 4.9; it lists outdated packages) or `npm outdated --json` (read-only; it does not touch the lockfile). |
| `yarn install --frozen-lockfile` | `yarn install --immutable` (CI uses `yarn --immutable`) |

---

## Options Considered

### Option A: Manual, per-package upgrades driven by audit and outdated output
Use `yarn up <pkg>` (respects the existing range) or `yarn up <pkg>@<range>` for each package, in the three stages. Commit after each stage (stages 1 and 2) or after each package (stage 3).

**Pros**: Exact control over commit contents. This satisfies the "one package per major commit" and revert-and-defer criteria directly.
**Cons**: More commands and more manual bookkeeping.

### Option B: Bulk tooling (`yarn up '*'`, `yarn upgrade-interactive`, or Renovate/Dependabot)
Update everything at once, or add an automation bot.

**Pros**: Fast.
**Cons**: `yarn up '*'` ignores the staging and can cross majors. A bot adds a new tool, which is out of scope, and `yarn up '*'` cannot isolate failures.

**Chosen**: Option A. Bulk steps are allowed only inside a stage where the semver range guarantees the same major (stage 2), and each is verified before commit.

## Files to Modify

| File | Change |
|---|---|

## Implementation

### 0. Baseline (before stage 1, not committed)

On a clean tree on branch `fix/update-dependencies`, record the following for later comparison and for the PR description:

```bash
yarn install --immutable
yarn npm audit --all --recursive --json > $SCRATCH/audit-before.json   # advisories: package, severity, fixed version
npm outdated --json > $SCRATCH/outdated-before.json                    # read-only
yarn test:coverage                                                      # note coverage % (src/coverage/)
/usr/bin/time yarn build                                                # note build time
du -sk src/dist/frontend                                                # note bundle size (check actual output path after build)
```

Also run a smoke test of `yarn dev`, as in Verification below, to confirm the baseline works. If lint, test or build already fails at baseline, record it. Do not attribute it to the stages.

### 1. Stage 1: vulnerability fixes

1. Run `yarn npm audit --all --recursive` and copy the advisory list (package, severity, fixed version) into the commit body (AC 1.1).
2. For each direct dependency with a fix inside its current range: `yarn up <pkg>`. This updates `yarn.lock` and bumps the range in `package.json` where needed (AC 1.2).
3. For transitive vulnerable packages with an in-range fix, `yarn up -R <pkg>` refreshes just the lockfile entry (the `-R` flag is `--recursive`, which also updates the dependents' transitive entries).
4. If the fix requires a major bump, defer it to stage 3 and note it. If it needs a `resolutions` entry, add it and document the reason in the commit body (AC 1.3). Prefer deferring over overrides.
5. Run `yarn npm audit --all --recursive --severity high`. It must report nothing, except advisories with no available fix; list those in the commit body (AC 1.4).
6. Run the full verification gate. Commit only `package.json` and `yarn.lock`:

```
build(deps): fix vulnerable dependencies

<advisory list>
```

### 2. Stage 2: minor and patch updates

1. Generate the outdated list (`npm outdated --json` or `yarn upgrade-interactive`) and keep only entries where `latest` has the same major as `current` (AC 2.1). Note that `^0.x` ranges treat minors as breaking, so for `0.x` packages (for example `eslint-import-resolver-node` and `neostandard`) check the changelog and treat a minor as potentially breaking; defer if unclear. `@mui/styles` is pinned to `6.4.8` and `@types/d3` to `^7`, so check each of them explicitly.
2. Apply with `yarn up <pkg>@^<latest>` for each package, or a batched `yarn up pkg1 pkg2 ...` for related groups (for example `@mui/*`, `@babel/*`, `@commitlint/*`, `@testing-library/*`, `vitest` with `@vitest/coverage-v8`, `react` with `react-dom` and their types), so each pair lands consistently.
3. Run the gate after each group. If a group fails, `git checkout -- package.json yarn.lock` for that group, bisect to the offending package, revert only it, add it to the deferred list with the failure reason, and continue (AC 2.3).
4. Rerun the audit to confirm no new high or critical advisories.
5. Commit all stage 2 changes together (AC 2.2, 2.4):

```
build(deps): update minor and patch dependencies

Deferred: <pkg> (<reason>)
```

### 3. Stage 3: major updates, one per commit

1. Compute the list of packages whose `latest` has a higher major. Order them by dependency and risk so tooling comes before the code that depends on it: type-only packages and small utilities first (`@types/*`, `dotenv`, `query-string`), then test and lint tooling (`vitest`, `@vitest/coverage-v8`, `jsdom`, `eslint`, `neostandard`, `eslint-plugin-import`), then build tooling (`webpack` family, `babel-loader`, `ts-loader`, `typescript`), then runtime libraries (`express`, `winston`, `graphql-request`, `@octokit/graphql`, `d3`, `@mui/*`, `react*`, `react-router`, `zustand`, `msw`). Packages that must move together (`react`/`react-dom`/`@types/react*`, `vitest`/`@vitest/coverage-v8`, `@mui/material`/`@mui/icons-material`, `eslint`/`@eslint/*`) form one unit and one commit. Note this exception in the commit body.
2. For each unit:
   - Read the changelog or migration guide first. Record the breaking changes that apply in the commit body (AC 3.1).
   - `yarn up <pkg>@^<newMajor>`. Check that no peer-dependency warnings regress: `yarn install` prints `YN0060` warnings, and compare them with the baseline. If there is an unresolvable peer conflict, revert and add the package to the deferred list with the blocker (AC 3.3).
   - Make the minimal code or config changes needed (AC 3.2). Test changes are limited to API changes of the upgraded package.
   - Run the full gate. If it fails and cannot be fixed within the scope of the package, revert and defer.
   - Commit only this package and related changes (AC 3.4):

```
build(deps): bump <pkg> from <old> to <new>
```

3. After all units are done, assemble the deferred list (pkg, current, latest, blocker) for the PR description (AC 3.5).

### 4. PR description

Include: pre-change advisory table (from step 0), stage summaries, deferred packages with reasons, breaking-change notes, any `resolutions` or `engines` change, and baseline versus final coverage, build time and bundle size (NFR: no more than a 10% regression, unless justified).

## Key Technical Decisions

- **Yarn 4 commands instead of the requirements' Yarn 1 commands**: `yarn audit`, `yarn outdated` and `--frozen-lockfile` do not exist in Yarn Berry. The equivalents are listed in Context. This also matches CI (`yarn --immutable`).
- **`npm outdated` is allowed as a read-only query**: Yarn 4 core has no outdated command. `npm outdated` does not modify `yarn.lock` and the install still goes through Yarn. Using `yarn upgrade-interactive` is an equally valid alternative.
- **Prefer deferral over `resolutions`**: overrides hide incompatibilities and need long-term tracking, so they are used only when no fixed version in range exists and the vulnerability is high or critical.
- **Stage 2 is one commit, stage 3 is one commit per package**: stage 2 changes are backwards-compatible, and reverting a failing package inside the stage keeps the commit clean. Stage 3 needs per-package bisecting.
- **`@mui/styles` is pinned to `6.4.8`**: it was deprecated and does not support MUI v7 or React 19 officially. Leave it pinned and do not treat it as outdated unless a replacement is clearly required. Record it as deferred if a major audit finding touches it.
- **Node engine**: `engines.node` is `>=18.12.0`, the dev container uses Node 22, and CI uses `vars.NODE_VERSION`. A major bump that drops older Node versions is acceptable only if CI and the dev container satisfy it. Document it, and update `engines` only if needed.
- **Workspace entry `src`**: `workspaces: ["src"]` has no matching `package.json`. It is out of scope (no unrelated refactoring), so leave it unchanged.

## Tests to Add

No new tests. The requirements state that the existing Vitest suites must pass unchanged in stages 1 and 2, and that stage 3 test changes are limited to API changes of the upgraded package. Existing suites that act as the regression gate:

- **Setup**: MSW-mocked GitHub API for the OAuth routes (`/login`, `/auth/github/callback`) and `/api/repo/:owner/:repo`.
- **Assert**: all pass unchanged after every commit, covering Express, `express-session`, `graphql-request`, `winston`, `msw`.

### Test 2: existing frontend suite (`src/vitest.config.frontend.ts`)
- **Setup**: JSDOM environment with React Testing Library.
- **Assert**: all pass unchanged, covering React, MUI, D3 charts, `zustand`, `react-router`.

### Test 3: coverage check
- **Setup**: `yarn test:coverage` after each stage.
- **Assert**: coverage is not lower than the baseline from step 0.

## Verification

Run after each stage and after each stage 3 commit:

```bash
# 1. Clean, reproducible install
yarn install --immutable

# 2. Lint
yarn lint

# 3. Full test suite (and coverage vs. baseline)
yarn test
yarn test:coverage

# 4. Build (compare time and bundle size with baseline)
yarn build

# 5. Security
yarn npm audit --all --recursive --severity high
```

Manual smoke test (requires local certs from `src/backend/certs/generate-certs.sh`, `src/.env` with GitHub OAuth credentials):

1. `yarn dev`. The server must start on `https://localhost:3000` and serve the frontend.
2. `curl -k -i https://localhost:3000/api/repo/<owner>/<repo>` must respond (for example 401 when unauthenticated) rather than crash.
3. In a browser, log in with GitHub OAuth, load a repository, and confirm the D3 bar charts render with no new console errors.
4. `yarn build && yarn start` must also serve the production bundle.

A stage is committed only when every step passes, or the offending package has been reverted and deferred.
